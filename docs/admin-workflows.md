# 系统后台操作与处理流程

本文对应 2026-09-25 main 源码。「系统后台」指 DBoard 管理后台；「探针后台」指整合后的 Nezha 监控后台。

相关文档：[用户流程](user-guide.md) · [安装](installation.md) · [运维与排错](operations.md) · [探针技术说明](../probe/README.md)

## 1. 各组件负责什么

| 组件 | 职责 |
| --- | --- |
| DBoard 面板 | 用户、套餐、权限组、订单、节点配置、实际计费、机器管理和探针接入设置 |
| 用户端 frontend | 商店、购买确认、套餐卡片、订阅和订单界面 |
| DUI-Gateway（可选） | 用户网页 API 路径加密与转发、指定的订阅/支付通知直通 |
| Probe Dashboard | 监控网页、gRPC 上报、节点管理通信桥接、后台入口验证 |
| Probe Connector | 在面板所在环境主动连接探针，把允许的请求转到本机面板 |
| 整合 Agent | 一个程序运行 Nezha 监控与 DBoard 节点功能，负责代理内核、监控、配置和流量报告 |

~~~mermaid
flowchart TB
  U[用户网页] -->|HTTPS API，可经过 DUI| P[DBoard 面板]
  A[DBoard 管理员] --> P
  P -->|控制 API：身份、排序、删除、授权| G[探针网关与监控后台]
  C[面板本机 Connector] -->|主动建立加密 WebSocket| G
  C <-->|仅回环 HTTP 与节点 WebSocket| P
  N[整合 Agent] <-->|HTTPS、WebSocket、gRPC| G
  V[用户代理客户端] --> N
  N --> R[节点路由选择的出口或落地]
  R --> T[目标网站]
~~~

图中的双向箭头表示建立连接后双向传输。Connector 的远程连接由面板侧发起；节点不需要拿到面板域名、内部机器 ID 或机器 Token。

## 2. 首次配置的建议顺序

1. 完成面板、探针、Connector 和 HTTPS 部署，确认「探针管理 → 检查连接」正常。
2. 在服务器管理添加服务器，执行该服务器生成的探针安装命令。
3. 确认服务器监控和节点通道均在线。
4. 建立权限组，设置节点和套餐的访问关系。
5. 创建入口节点并绑定服务器；需要时创建独立落地分区与其中的管理分组。
6. 配置出站、路由规则和需要的前置认证。
7. 建立套餐、价格、库存显示、流量和设备限制，预览套餐说明。
8. 配置支付、订阅域名、用户须知等用户端内容。
9. 用测试账号完成新开、原卡片续费、商店续费和订阅连接验收。

「管理分组」用于管理和筛选；「权限组」决定用户/套餐可用的节点。两者不能互相替代。

## 3. 服务器管理的完整生命周期

### 添加服务器

1. 启用探针接入后，在「节点管理 → 服务器管理」添加服务器。
2. 面板保存内部机器记录和探针 UUID，通过认证控制 API 创建真实 Nezha 服务器。
3. 生成包含探针地址、UUID、一次性 enrollment 和 Agent 版本的命令。
4. 在目标服务器执行；安装器从探针下载程序，校验 SHA-256 并完成注册。
5. Agent 保存本机专属密钥，启动监控 gRPC 与节点通道。
6. 后台看到在线后，再创建或绑定业务节点。

安装命令约 15 分钟有效。过期应重新生成，不要把别台机器的命令用于新服务器。

新建探针服务器默认对访客隐藏。管理后台能看到机器，但公开监控首页未必能看到；需要公开时通过授权后的探针后台调整访客可见性。

### 显示 ID 与排序

- 拖动排序保存后，面板调用探针批量排序接口，更新探针的默认顺序。
- 探针用户自行选择其他排序方式时，显示顺序可能不同；核对同步结果请切回默认排序。
- 可勾选「按当前排序从 1 重新分配显示 ID」，预览后保存。
- 显示 ID 用于列表、详情与绑定选择；内部 SID、UUID、节点关联和 Token 不变。
- 探针自己的内部数据库 ID 不会重新编号。
- 只有全部排序数据完整且探针确认成功才提交；失败会提示重试并回滚面板本次变更。
- 显示 ID 重新编号之后，新服务器从当前序列继续分配。

### 删除服务器

面板先请求探针撤销身份并清理监控记录，再删除本地机器记录和处理节点绑定。

- 探针没有确认时，面板保留记录并报错，可重试。
- 已删除身份保留不含凭据的注销标记，防止旧程序重新接入后生成残留机器。
- 重复删除可安全重试。
- 删除服务器记录不等于远程卸载 VPS 上的程序；本地服务可能继续尝试连接，但旧身份会被拒绝。
- 应从 DBoard 服务器管理执行生命周期操作，避免只在探针端删除后两边记录不一致。

## 4. 探针后台必须从系统进入

操作路径：**系统管理 → 探针管理 → 监控后台 → 进入监控后台**。

1. 浏览器向 DBoard 发起管理员鉴权的 POST 请求。
2. DBoard 用服务端对接密钥向探针申请一次性授权。
3. 浏览器新窗口把授权通过 POST 交给探针，授权不放在 URL 查询参数里。
4. 探针消费授权并设置 Secure、HttpOnly、仅当前主机有效的 Cookie。
5. 跳转探针后台；仍由探针原有账号认证决定能否登录和执行管理操作。

| 项目 | 当前行为 |
| --- | --- |
| 一次性授权 | 60 秒有效，只能消费一次 |
| 入口会话 | 2 小时；进程重启后失效 |
| 未授权访问后台页面/资源/登录 API/管理 API | 返回 404 |
| 普通用户向 DBoard 申请授权 | 拒绝 |
| 已有 Nezha JWT/PAT，但没有入口会话 | 不能单独访问管理接口 |
| 公开首页 | 无登录/管理入口，按既有访客可见性展示 |
| 已授权浏览器 | 会话有效期间可继续访问后台，无须每次操作都点一次系统入口 |

这不是依据 Referer 判断，也不是只隐藏链接。不要通过反向代理例外或开放旧登录路径绕过入口层。

## 5. 节点配置、前置、落地与分流

### 把系统节点作为出口

1. 创建落地节点并绑定其服务器。
2. 编辑入口节点，打开「高级配置 → 出站规则」。
3. 点击「选择现有节点」展开，再次点击可收起。
4. 通过搜索或管理分组筛选落地，勾选后加入所选节点。
5. 将出口用于路由规则或负载均衡，保存入口节点。
6. 等待配置下发，再进行 TCP/UDP 和实际业务测试。

可以选择系统节点，也可以在出站规则管理中创建第三方出口后选用。

### 只允许指定前置使用落地

1. 在落地节点的绑定服务器下方启用「仅允许指定前置」。
2. 选择一个或多个前置节点，或选择套餐所使用的权限组。
3. 后端动态识别权限组内符合条件的前置；显式选择与组成员取并集。
4. 在前置出站中选择该系统落地节点，并设置需要的路由。
5. 系统向获准前置下发专属身份，落地验证前置证书，前置也验证落地身份。

此模式使用受管的双向 TLS 身份验证；授权列表只定义「谁可以接入」，不会自动决定「哪些用户流量走哪里」。因此还需要前置的出口/路由配置。用户拿普通订阅链接自行链式，不会获得内部证书。

保护模式使落地原监听端口使用内部认证协议，普通客户端不能直接连这个端口。已有分流、出口标签和计数继续由节点配置执行。详见[前置认证说明](front-gate-worklog.md)。

### 指定用户与跳过用户

- 用户选择默认只列出当前拥有该节点有效套餐访问权的用户，多份套餐合并显示。
- 指定用户留空表示适用全部用户。
- 「跳过用户」从该规则适用范围中排除所选用户。
- 被排除用户继续匹配后续规则或默认出口；不等于必然直连。
- 逐项核对具体用户规则、通用规则和默认出口，避免前一条规则已匹配导致后续规则无效。
- 新节点需要先保存，后端才能根据真实节点权限提供用户候选。

## 6. 流量统计分别统计什么

| 统计位置 | 统计范围 |
| --- | --- |
| 用户套餐 | 按用户身份和计费配置扣量 |
| 节点上的出口卡片 | 当前节点使用该出口的独立累计，建立绑定后开始跟踪 |
| 出站规则管理的第三方出口 | 该全局出站对象的累计使用量 |

第三方出口同时影响对应节点的局部统计与出站管理的全局统计。系统节点出口也有节点侧独立统计。两个视图是不同范围的汇总，不要相加后当作用户额外消费。

节点增量上报有批次身份；面板在数据库事务中保存计费和回执，相同批次重试不重复扣量。出口累计统计保留自己的游标和累计逻辑。

## 7. 套餐、库存和说明编辑

1. 为套餐选择权限组、流量、速度、设备数及需要的连接数限制。
2. 设置容量上限；「剩余名额」是容量减去未到期或长期有效的套餐记录数，最低为 0。
3. 选择库存显示方式：
   - 原有状态模式保留兼容行为，以配置容量和前端阈值生成标签，不能当作精确实时剩余人数。
   - 剩余数模式使用后台计算的 capacity_remaining。
4. 填写需要销售的周期价格；留空的周期不显示，明确的 0 元不会被当作留空。
5. 流量包和重置包各自填写价格；不填写时模板中对应行自动隐藏。
6. 套餐说明支持原有 Markdown/HTML；编辑器支持文字颜色、背景色、字号等，使用模板后预览替换效果。

仅修改展示费率不会修改实际扣量倍率。实际倍率、动态倍率和展示值分别按配置使用，运维时应核对计费结果。

## 8. 下单、支付与开通如何处理

~~~mermaid
sequenceDiagram
  participant U as 用户端
  participant P as DBoard
  participant DB as 数据库
  participant Pay as 支付渠道
  U->>P: 查询套餐报价与购买入口
  P-->>U: 周期、价格、库存与目标信息
  U->>P: 提交订单
  P->>DB: 锁定账户/目标，重新报价，保存订单
  P-->>U: 订单号与应付金额
  U->>Pay: 按订单完成支付
  Pay->>P: 支付回调
  P->>DB: 校验订单状态并记录支付
  P->>DB: 开通/续费/重置，更新完成状态
  U->>P: 查询订单与套餐卡片
  P-->>U: 返回最新状态
~~~

后端不直接信任浏览器显示的金额。创建订单时重新获取套餐和专属价格，并校验目标归属、同款关系、可售状态与容量。

- 商店新开/续费：按商店价格报价。
- 原卡片续费：套用该份套餐保存的周期专属价格，没有专属项时回退标准价。
- 订单保存购买入口、报价、续费前到期时间和目标身份。
- 支付回调与开通有状态锁和幂等保护。当前 paid() 主路径在事务提交后通过 dispatchSync 执行开通，不是只排队等待；异常仍需检查订单处理日志，其他队列/调度任务也应保持正常。
- 余额、优惠券和会员折扣可能影响应付金额。
- 周期续费还会应用套餐额度及限制；纯延时的管理员操作与普通购买续费应区分。
- 管理员改价应明确改的是商店价格，还是某个用户持有套餐的专属续费价格。

用户端订单和活动展示经过过滤。前端显示异常时，先核对订单数据与资源转换，再看主题渲染。

## 9. 改探针地址、升级和故障恢复

- 新域名与备用域名必须先配置证书及 gRPC/WebSocket 转发，再在「更新连接地址」中选机器下发。
- 在线机器校验新地址后保存重连；离线机器保留任务，恢复旧/备用连接后才能收到。
- 所有已知域名同时不可达时，节点无法凭空获知新地址，需要恢复已知入口或本机修改。
- 跨主机迁移要同时迁移监控数据库、身份注册表和对接密钥。
- Agent 目标版本来自探针设置及探针上已准备的文件，不等同于 GitHub main 最新提交。
- 面板/探针后台修改与节点升级分别判断，不要每次改 UI 都批量重启节点。

完整命令、备份清单和排错顺序见[运维指南](operations.md)。
